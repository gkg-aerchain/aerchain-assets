Overview
Executive Summary

Aerchain integrates with Adani's existing SAP ERP and SAP Ariba ecosystem to deliver a unified, AI-powered vendor intelligence layer — without requiring Adani to decommission or replace its current systems overnight. This document details three integration scenarios covering clean replacement, co-existence, and hybrid modes, along with the technical architecture, data field mappings, and a phased implementation roadmap.

Key Principle: Aerchain Augments, Not Replaces
Aerchain acts as the vendor intelligence and qualification layer on top of Adani's existing systems. SAP remains the system of record for approved vendor master data. Ariba can continue to serve existing vendors during transition. Aerchain provides onboarding, scoring, and event participation — and triggers SAP vendor master creation at the point of award.

As-Is
Current State Architecture

Adani's current vendor management stack uses two distinct systems with a clear handoff point: SAP Ariba manages vendor onboarding and sourcing events, while SAP ERP holds the approved Vendor Master. The key challenge is the identity gap — two separate vendor IDs across two systems, with a large population of Ariba-only vendors who have never been promoted to SAP.

The Identity Gap: Two Vendor Identifiers

Ariba Network ID (ANID)

  • Assigned by SAP Ariba Network at vendor registration
  • Exists for all vendors — including those who never won an event
  • Not present in SAP ERP for non-award vendors
  • Format example: AN01234567890

SAP Vendor Master ID

  • Created in SAP only upon sourcing event award
  • Primary key for all downstream procurement (POs, invoices)
  • Typically numeric, company-code specific
  • Format example: 1000XXXXXX
Identity Gap: A significant vendor population exists in Ariba (with ANID) but has no SAP Vendor Master ID — they were onboarded but never awarded. These vendors are an unmapped pool that requires a clear handling strategy during the Aerchain migration.

Options Analysis
Aerchain Integration Scenarios

Three integration scenarios have been defined based on Adani's migration ambition and timeline. Each has different system ownership, data flow, and complexity implications.

Scenario 1 — Recommended for New Vendor Categories
Clean Replacement: Aerchain Replaces Ariba Onboarding
Vendors register, onboard, and participate in sourcing events entirely on Aerchain. SAP Ariba has no role in the new vendor journey. Upon award, Aerchain directly pushes the vendor record into SAP for Vendor Master creation. This is the cleanest integration path — no Ariba dependency, no ID reconciliation needed.
1
Vendor Self-Registration on Aerchain
Vendor registers on Aerchain's self-service portal, submits documents, completes compliance checks. Aerchain assigns its own Vendor ID (ACID).
2
Qualification & AVL Tagging
Aerchain scores the vendor — Approved (>70), Qualified (50-70), or Qualified with CAPA (<50). Category and location tags assigned to AVL.
3
Sourcing Event on Aerchain
Buyer creates RFQ/RFP/Auction on Aerchain. Qualified vendors from AVL are invited. Bidding, negotiation, and award handled on Aerchain.
4
Award Trigger → SAP Vendor Master Creation
On award confirmation, Aerchain pushes vendor record via SAP REST API or IDoc. SAP creates Vendor Master record and returns the SAP Vendor ID, stored back in Aerchain.
No Ariba Dependency Clean Data Model Recommended for New Vendors Requires Ariba Decommission Plan
Scenario 2 — For Existing Vendor Population
Co-existence: Ariba Remains for Existing Vendors
Existing vendors already in Ariba and/or SAP continue to be managed in those systems. Aerchain co-exists with a mapping layer that reconciles the Ariba Network ID (ANID) to the SAP Vendor Master ID. Vendors that are Ariba-only (no SAP ID) are either migrated to Aerchain or kept in Ariba as a read-only repository.
1
Vendor Data Migration / Mapping
Aerchain ingests Ariba vendor export (ANID + profile data) and SAP Vendor Master export. A reconciliation engine maps ANID to SAP Vendor ID where both exist.
2
Ariba-Only Vendors: Decision Point
Vendors with ANID but no SAP ID: (A) Migrate — invite them to re-register on Aerchain portal, or (B) Freeze — keep in Ariba as read-only archive, ineligible for new events.
3
Dual-Source Sourcing Events
New events run on Aerchain. Existing approved vendors from Ariba/SAP are imported into Aerchain's AVL. ANID stored as reference attribute on the Aerchain vendor profile.
4
Award & SAP Sync
For existing SAP vendors: award notification sent, no new Vendor Master creation needed — SAP ID already exists. For migrated vendors: standard Scenario 1 flow applies.
Requires ANID / SAP ID Reconciliation Supports Existing Vendor Base Most Complex — Dual System State Lowest Migration Risk
Scenario 3 — Recommended Long-Term Target State
Hybrid: Aerchain as System of Record + SAP Master Creation
Aerchain becomes the single system of record for all vendor onboarding, qualification, and sourcing — for both new and migrated vendors. SAP remains the ERP of record. Ariba's ANID is preserved as a reference attribute in Aerchain and passed to SAP as a reference field (not the primary key). This is the target architecture for Adani's long-term procurement stack.
1
Aerchain as Single Vendor Intake Channel
All new vendor registrations go through Aerchain. Existing Ariba vendors are migrated in a phased approach with ANID preserved as metadata.
2
ANID as Reference Attribute
For vendors migrated from Ariba, the ANID is stored in Aerchain's vendor profile as a reference field. The Aerchain Vendor ID (ACID) is the new primary identifier.
3
Aerchain to SAP Integration on Award
API-based push to SAP on award. Aerchain sends vendor master payload including ANID reference field. SAP creates/updates Vendor Master and returns the SAP Vendor ID.
4
Bi-directional Sync (Optional)
SAP Vendor Master updates (bank changes, status changes) can be synced back to Aerchain via scheduled API polling or event-driven webhook, keeping profiles current.
Target Architecture Single System of Record ANID Preserved as Reference Bi-directional SAP Sync Available

🔑
ANID Handling: Reference Attribute, Not Primary Key
The Ariba Network ID (ANID) is stored in Aerchain as vendor.anid — a searchable reference attribute on the vendor profile. When Aerchain pushes a vendor to SAP on award, the ANID is passed in a custom reference field (e.g., ZXREF1 in the LFB1 table) for traceability. The ANID is never used as a primary key in SAP — it serves only as a cross-reference for audit and migration purposes. This design ensures backward compatibility with any Ariba reporting while maintaining SAP data integrity.

Execution Plan
Implementation Approach & Phasing

The recommended implementation follows a phased approach — starting with a contained pilot on new vendor categories, expanding to cover migrated Ariba vendors, and concluding with full go-live and Ariba sunset. Estimated total timeline: 16–20 weeks from kickoff to full production.

1
Phase 1
Discovery & Integration Design
Weeks 1–3
  • SAP system landscape assessment (ECC vs S/4HANA, Gateway availability)
  • Ariba data export — vendor count, ANID inventory, completeness audit
  • SAP Vendor Master field mapping workshop with Adani IT
  • Decision on integration method: API-based vs file-based
  • Data migration scope: which Ariba vendors to migrate vs freeze
2
Phase 2
Platform Configuration & Integration Build
Weeks 4–9
  • Aerchain tenant provisioning for Adani — portal branding, category taxonomy
  • Qualification criteria configuration — scoring weights, CAPA rules
  • SAP integration connector configuration (API credentials, field mapping, error handling)
  • Custom SAP field extension for ANID reference (ZXREF1 in LFB1)
  • Ariba data ingestion pipeline for bulk vendor migration
3
Phase 3
UAT & Pilot Go-Live (New Vendors)
Weeks 10–13
  • End-to-end UAT: vendor registration to qualification to RFQ to award to SAP creation
  • SAP Vendor Master validation — test records in SAP QA environment
  • Pilot go-live with 1-2 new vendor categories (Scenario 1)
  • User training for Adani procurement team and vendor portal orientation
4
Phase 4
Ariba Vendor Migration & Full Go-Live
Weeks 14–18
  • Bulk migration of in-scope Ariba vendors to Aerchain AVL (ANID preserved)
  • Vendor re-registration campaign for Ariba-only vendors selected for migration
  • ANID to SAP Vendor ID reconciliation for dual-ID vendors
  • Full production go-live across all vendor categories
  • Ariba transition to read-only / archive status
5
Phase 5
Hypercare & Optimization
Weeks 19–20 + Ongoing
  • Hypercare support — dedicated Aerchain resource for first 4 weeks post go-live
  • Integration monitoring dashboard — SAP push success rate, error tracking
  • Bi-directional SAP sync enablement (optional — Scenario 3 advanced feature)
  • Quarterly scoring and AVL review with Adani procurement leadership

Key Risks & Mitigations

R1
Incomplete Ariba Export Data
Risk: Ariba vendor records may have incomplete fields (missing PAN, bank details) causing SAP push failures. Mitigation: Data quality audit in Phase 1; mandatory field validation before migration batch runs.
R2
SAP Custom Field Approval Delay
Risk: SAP BASIS team may require extended change management for the custom ANID reference field. Mitigation: Initiate SAP change request in Week 1; design fallback using existing SAP note/reference fields.
R3
Ariba Vendor Re-Registration Drop-Off
Risk: Ariba-only vendors may not complete re-registration on Aerchain, reducing the active vendor pool. Mitigation: Phased communication campaign with procurement team sponsorship; CAPA exemption for re-registering vendors in first 90 days.
